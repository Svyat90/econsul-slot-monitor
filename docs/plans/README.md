# Плани

Тут — плани, що зачіпають кілька модулів. План одного модуля лежить у `<модуль>/plans/`.
Ідеї до плану проходять брейншторм (`brainstorm/ideas.md`); план стає джерелом правди, щойно
його погоджено.

| План | Статус |
|---|---|
| [web-rewrite-plan.md](web-rewrite-plan.md) | погоджено 2026-10-09; виконано повністю 2026-10-21 |

## Як план виконується

**Нові плани (з 2026-10-21)** — процесом плагіна `sdd-engineering`: агент `spec-creator` пише
специфікацію, `implementation-planner` — план у його форматі, скіл `run-plan` роздає задачі агентам
`implementer` і після хвиль запускає `plan-verifier` і `architecture-reviewer`
(`architecture-review`). Формат плану й задачі — той, що в плагіні; проєктні обмеження агенти беруть
із `CLAUDE.md`, `docs/conventions.md` і `.claude/paved-path.json`.

**Старий формат** нижче — для [web-rewrite-plan.md](web-rewrite-plan.md), що писався до плагіна
(локальних агентів із ним більше немає; лишилась одна задача S8.T5 — видалення старого):

1. План описує етапи (що має з'явитися і як це перевірити).
2. **Перед етапом** основна сесія розбиває його на задачі — розділ `## Етап N — задачі` у самому
   плані за шаблоном нижче — і показує користувачу.
3. Задачі однієї хвилі (`Wave`) з файлами, що не перетинаються, виконують агенти
   `implementer` паралельно, у тому самому робочому дереві.
   Агенти не комітять: основна сесія комітить кожну задачу окремо.
4. Після останньої хвилі паралельно запускаються
   `plan-verifier` (чи зроблено все, що в плані) і
   `architecture-reviewer` (чи не порушено кільця й
   межі). Їхні знахідки стають задачами виправлення `F<раунд>.<n>` у розділі
   `## Журнал виконання` плану.
5. Етап закрито, коли `plan-verifier` каже `VERIFIED`, а `architecture-reviewer` — `PASS`.
   Відмітка про це — у `## Журнал виконання`.

## Шаблон задачі

Назви полів — англійською (їх читають агенти), зміст — як зручно.

````markdown
## Етап 3 — задачі

### Wave 1 — паралельно

#### S3.T1 — <назва>
- Module: web | server | extension
- Depends on: — | S3.T0
- Files (exclusive):
  - `web/src/domain/slots/schedule-days.ts` (new)
  - `web/src/domain/slots/schedule-days.test.ts` (new)
- Rules (5–15 рядків; агент застосовує їх замість читання скілів цілком):
  - <одне конкретне правило, яке можна перевірити> — <skill> §<section>
- Interface (лише коли інша задача викликає те, що тут експортується):
  - `buildScheduleDays(input: ScheduleDaysInput): ScheduleDay[]` — exported here
- Designs (для задач інтерфейсу): `web/docs/design/slots.png`
- Steps:
  1. <тест, що він перевіряє>
  2. <зміна>
- Acceptance criteria:
  - <поведінка, яку видно ззовні>
- Verify:
  - `pnpm --dir web exec vitest run src/domain/slots/schedule-days.test.ts`
  - `pnpm --dir web run typecheck`
- Constraints (цитати, а не посилання — агент не читає insights цілком):
  - <назва інсайту> — <його правило> — `<модуль>/INSIGHTS.md` (<дата>)
  - <інваріант з `docs/booking.md` §… дослівно>
````

Правила:

- Кожен файл належить рівно одній задачі етапу (таблиця `Ownership` наприкінці розділу).
- Одна задача — один модуль. Задача на два модулі — дві задачі із `Depends on`.
- Тести пише той самий `implementer`, що й код (спершу тест, що падає).
- Команди в `Verify` — лише ті, що не змінюють спільний стан: без `pnpm install`, `docker`,
  `db:migrate`, запуску серверів.
