## 1. Коротко

- Сайт отримує дані календаря **двома тими самими запитами**, що й програма:
  `public-calendar-get-actual-consuls-schedule` (розклад) і `public-get-consuls-reserved-slots`
  (зайняті записи).
- Вільні слоти **рахуються в браузері**, у web worker, а не на сервері.
- Стара версія програми рахувала інакше: 5-хвилинна сітка, лише перший запис розкладу, без
  урахування послуги, періодів розкладу, горизонту і свят. Через це вона знаходила «вікна»,
  яких на сайті немає.
- Нова версія повторює алгоритм сайту. Звірка із сайтом через його власний календар:
  **Чикаго і Г'юстон збіглися повністю**, і за днями, і за кожним вільним слотом (розділ 11).
- Параметри всіх 130 установ (код, часовий пояс, горизонт, тривалість кожної послуги) збережені
  в `locations.json`. В інтерфейсі країна, установа і послуга вибираються зі списків.
- Сторінка вміє стежити за вибраною установою: перевірки з випадковим інтервалом (за замовчуванням
  60–180 с, а навколо щоденного відкриття нового дня — кожні 15–20 с), звук і нотифікація про нові слоти, окремий звук і нотифікація, коли сесія скінчилась,
  і журнал змін розкладу консулів у `logs/schedule-changes.jsonl` (розділ 9, «Моніторинг»).
- Бронювання на сайті — це не окремий запит, а ланцюжок задачі: створення задачі, збереження
  документа на кожному кроці, `external-reader/check` з методом `public-check-and-book-appointments`
  і `commit`. Дані для бронювання сервер бере з документа задачі. Запити поза браузером Cloudflare
  блокує, а `Origin` запиту з програми відрізняється від сайту (розділ 14).
- Кнопка **↗ Book on e-consul** і клік по нотифікації про нові слоти відкривають у новій вкладці
  підготовлену чернетку з поля **Draft link** (кроки 1–3 заповнені на сайті заздалегідь), а якщо
  його немає — нову заявку «Запис на візит». Заповнювати чернетку прямими запитами до API не варто
  (розділ 14.7).

## 2. Як влаштований сайт

### Кроки запису

Запис на візит — це задача (`/tasks/{taskId}/...`) з чотирма кроками:

| Крок | Шлях | Що вибирається |
|---|---|---|
| 1 | `applicantInfo` | Дані заявника |
| 2 | `placeOfVisitInfo` | Країна та консульська установа |
| 3 | `consularServiceInfo` | Послуга; «для себе» чи «для дитини/підопічного» |
| 4 | `dateAndTimeVisitInfo` | Дата та час візиту (календар) |

Після вибору послуги на кроці 3 сайт виконує перевірку («Зачекайте, будь ласка, відбувається
перевірка»). Вона може заблокувати запис: «Запис на візит для отримання цієї послуги наразі
недоступний» або «Сервіс недоступний. Скористайтеся послугою пізніше».

Якщо вільного часу немає, на кроці 4 показується повідомлення
«На жаль, зараз немає вільного часу…» і кнопка «Записатись в чергу очікування». Якщо є,
календар показує тижні з лічильником «N вільних слотів», а для кожного дня — сітку слотів:
вільні виділені синім, зайняті сірим.

### Архітектура фронтенду

- Фронтенд — універсальний рушій форм (webpack-бандл `bpmn_front`, React + MUI + moment.js).
  Форми описані **JSON-шаблонами**, які сайт отримує з сервера.
- API розташований на `https://my.e-consul.gov.ua`.
- Авторизація: JWT у заголовку `token`. У браузері він лежить у `localStorage.token`.
  Без токена API повертає `401`.
- Що сайт завантажує під час роботи заявки:

| Запит | Призначення |
|---|---|
| `GET /auth/me` | Поточний користувач |
| `GET /tasks/{taskId}` | Задача та дані заповненої форми (`document.data`) |
| `GET /workflow-templates/161374` | Шаблон процесу «Запис на візит» |
| `GET /task-templates/161374001` | Шаблон задачі |
| `GET /document-templates/161374001` | **JSON-схема форми**, зокрема налаштування календаря |
| `POST /external_reader` | Дані з реєстрів: довідники, розклад, зайняті слоти |

- Розрахунок вільних слотів виконує окремий web worker (`worker.<hash>.worker.js`). Сторінка
  передає йому розклад і блокування, а він повертає `{ result: true | false }`.

## 3. API: запити та відповіді

Усі запити — `POST https://my.e-consul.gov.ua/external_reader` із заголовками
`content-type: application/json` і `token: <JWT>`, тіло `{ service, method, filters }`.

### 3.1. Розклад консулів

```json
{
  "service": "e-queue-register",
  "method": "public-calendar-get-actual-consuls-schedule",
  "filters": { "institutionCode": "1000000522" }
}
```

Відповідь: `{ "data": [ ...записи ], "meta": { "count", "offset", "limit" } }`.
Кожен запис — `{ id, registerId: 8, keyId: 17, createdAt, updatedAt, data: {...} }`, де `data`:

| Поле | Опис |
|---|---|
| `consulIpnHash` | Ідентифікатор консула (хеш) |
| `institutionCode`, `institutionName` | Установа |
| `receptionCitizensTime[]` | Години прийому по днях тижня: `{ workingDays: "понеділок", workingHoursFrom: "09:00", workingHoursTo: "12:00" }`. **Для одного дня тижня може бути кілька проміжків** (Нью-Йорк: понеділок 09:00–12:00 і 14:00–17:00) |
| `nonWorkingTime[]` | *(може бути відсутнім)* Неробочі проміжки: `{ notWorkingDateAndHoursFrom, notWorkingDateAndHoursTo }`, формат `2026-11-11T09:00:00.00-06:00` |
| `consularInstitutionService[]` | Послуги, які надає консул за цим записом розкладу: `{ id, code, name }` |
| `admissionSchedulePeriodDate` | *(необов'язкове)* Дата, **до якої включно** діє цей запис розкладу |

**Важливо:** для одного консула може бути кілька записів розкладу з різними періодами, наборами
послуг і неробочим часом. Приклад — Чикаго (`1000000522`) на 2026-10-08:

| # | Консул | Період до | Послуги (коди) | Години | `nonWorkingTime` |
|---|---|---|---|---|---|
| 0 | `556940f3…` | — | 7, 1, 60, 62, 4, 6 | пн–ср, пт 09:00–12:00; чт 09:00–11:00 | 192 |
| 1 | `556940f3…` | 2026-10-14 | 58, 7, 1, 60, 62, 4, 6, 2 | так само | 108 |
| 2 | `1df0fd87…` | 2027-01-06 | 39 послуг, без `1` | пн–пт 09:00–13:00 | 0 |
| 3 | `1df0fd87…` | — | 39 послуг, без `1` | пн–пт 09:00–13:00 | 0 |

Г'юстон (`1000000510`): консул `76e01698…` (паспорт) з двома записами (до 2026-12-29 і без
обмеження, пн–пт 09:00–13:00, `nonWorkingTime` немає) та консул `2b9382d0…` без паспортної послуги.

Для деяких установ сервер розклад не повертає. 2026-10-08 таких було 7: Гана, Фінляндія,
ДР Конго, Іран, Ліван, Нігерія та Еквадор (див. розділ 11); для Гани перевірено, що це відповідь
`500`. Програма показує таку відповідь як помилку `HTTP 500`.

### 3.2. Зайняті слоти

```json
{
  "service": "e-queue-register",
  "method": "public-get-consuls-reserved-slots",
  "filters": {
    "institutionCode": "1000000522",
    "status": [1, 2, 4, 5],
    "consulIpnHash": ["556940f34c39d4010255c227e32920f66a291d10542bc54c8724b85a3aa9cd6c"]
  }
}
```

Відповідь:

```json
{
  "data": {
    "status": "found",
    "reservedSlots": [
      {
        "consulIpnHash": "556940f3…",
        "receptionDateAndTimeFrom": "2026-03-10T10:10:00.00-06:00",
        "receptionDateAndTimeTo": "2026-03-10T10:20:00.00-06:00"
      }
    ]
  }
}
```

Сайт запитує зайняті слоти для **всіх консулів, які надають обрану послугу**. Статуси
`[1, 2, 4, 5]` беруться з даних заявки (`calculated.statusArray`).

## 4. Довідники: країни, установи, послуги

Кроки 2 і 3 заповнюються з трьох довідників (той самий `external_reader`, `filters: {}` повертає все):

| Метод | Що повертає | Ключові поля |
|---|---|---|
| `public-get-countries` | 98 країн | `code` (ISO 3166 numeric), `nameShort` |
| `public-get-institutions` | 131 установа | `unitId` (= `institutionCode`), `institutionNameUkr`, `countryCode`, `timeZone`, `numberWeeks` |
| `public-get-services-and-time` | 7494 записи «установа × послуга» | `consularInstitutionId` (= `unitId`), `serviceNumber`, `serviceName`, `serviceTime` |

Що варто знати:

- **`unitId` установи — це `institutionCode`**, який іде в запити розкладу й зайнятих слотів.
- **`serviceTime` — тривалість слоту** для цієї послуги в цій установі. Вона різна: для паспорта (`1`)
  буває 10, 15 або 20 хвилин.
- У Генерального консульства в Дрездені немає `unitId`, тому для запису воно непридатне і в
  `locations.json` не потрапило. Отже, у файлі 130 установ у 95 країнах.
- Поле `timeZone` подекуди не відповідає реальному поясу міста: Нью-Йорк і Сан-Франциско
  `GMT-07:00`, Торонто й Едмонтон `GMT-07:00`, Мексика `GMT-09:00`, Австрія, Сербія, Брно та
  Вроцлав `GMT-01:00`. Сайт використовує саме це поле (розділ 7), тому програма теж.

## 5. Налаштування календаря у шаблоні форми

Календар — це елемент `dateAndTimeVisitInfo.calendar` у JSON-схемі
`GET /document-templates/161374001` з контролом `schedule.calendar`:

| Параметр | Значення | Що означає |
|---|---|---|
| `service` / `method` | `e-queue-register` / `public-calendar-get-actual-consuls-schedule` | Звідки брати розклад |
| `keyId` | 17 | Реєстр розкладів |
| `timeSlotsSource` | `receptionCitizensTime` | Звідки брати години прийому |
| `disabledTimeSlots` | `nonWorkingTime` | Звідки брати неробочий час |
| `additionalDisabledSlotsRequest` | запит `public-get-consuls-reserved-slots` | Зайняті слоти додаються до неробочого часу |
| `groupBy` | `consulIpnHash` | Розклад групується за консулом |
| `scheduleEndDate` | `admissionSchedulePeriodDate` | Поле, яке обмежує період дії запису розкладу |
| `startDayMove` | `1` | Запис можливий із **завтрашнього** дня |
| `minDate` | `now` | Сьогодні |
| `maxDate` | `now + numberWeeks тижнів` | `numberWeeks` установи (25 або 26) |
| `slotInterval` | `serviceTime` послуги в установі | Для паспорта в Чикаго та Г'юстоні — 10 хв |
| `serviceNumber` | `consularServiceInfo.service.data.serviceNumber` | Код обраної послуги |
| `timeZone` | `consularInstitution.timeZone` | Наприклад, Чикаго `GMT-06:00` |
| `holidays` | функція від `calculated.registerOfHolidays` і коду послуги | Дні, коли запису немає |

> `minDate`, `maxDate`, `slotInterval`, `holidays` та інші параметри в шаблоні — це JavaScript-функції
> виду `(moment, value, step, documentData) => …`. Сайт виконує їх на даних заявки.

### Свята

Функцію `holidays` виконано для всіх 130 установ і всіх 58 послуг. Від установи вона не залежить,
від послуги — так. Актуальні дати на 2026-10-08:

| Послуги | Дні без запису |
|---|---|
| `1`, `60`, `62` (закордонний паспорт, зокрема дітям) | 2026-11-21 … 2026-11-27 та 2026-12-25 |
| усі інші | 2026-12-25 |

Решта дат у `registerOfHolidays` належить до 2024 року і вже не діє.

## 6. Як сайт будує дні календаря

Для кожного консула, який надає обрану послугу:

1. Записи розкладу з `admissionSchedulePeriodDate` сортуються за цією датою. Перший діє
   з `сьогодні + startDayMove` (завтра) до своєї дати **включно**, кожен наступний — з дня після
   кінця попереднього.
2. Запис без `admissionSchedulePeriodDate` діє після останнього періоду і до кінця горизонту.
3. **Горизонт.** День потрапляє в календар, лише якщо **час відкриття цього дня за `timeZone`
   установи раніше, ніж `зараз + numberWeeks тижнів − 1 день`**. Отже, останній день залежить
   від часу доби. Правило встановлене емпірично і підтверджене на сайті:
   - Чикаго (`GMT-06:00`) о 09:29 CDT: відкриття 31.03.2027 о 09:00−06:00 (= 10:00 CDT) пізніше
     межі 09:29 → останній день **30.03**, 117 днів;
   - Чикаго о ~10:30 CDT: відкриття 31.03 вже раніше межі → останній день **31.03**, 118 днів;
   - Г'юстон (`GMT-05:00`) о 09:50 CDT: відкриття 31.03 о 09:00−05:00 раніше межі → **31.03**, 118 днів.
4. Для кожної дати беруться **всі** проміжки `receptionCitizensTime` для її дня тижня; кожен
   проміжок — окремий блок слотів. Якщо проміжків немає (вихідний), дня немає в календарі.
5. Свята (розділ 5) пропускаються.

Кожен такий день передається worker'у як
`{ currentDate, start, end, timeZone, data: <запис розкладу> }`.

## 7. Як сайт перевіряє вільні слоти (web worker)

Сторінка передає worker'у повідомлення з такими полями (приклад — Чикаго, 09:29 CDT):

| Поле | Значення |
|---|---|
| `schedules` | 234 дні: усі консули, усі записи розкладу |
| `notWorkingDays` | 2128 блокувань = 300 `nonWorkingTime` + 1828 зайнятих слотів, кожне з `consulIpnHash` |
| `slotIntervalEval` | `10` |
| `serviceNumber` | функція, що повертає код послуги (`1`) |
| `availableServices` | `consularInstitutionService` |
| `ignoreTimezone`, `invertTime`, `ignoreSlotInterval` | `false` |

Алгоритм worker'а (спрощено):

```text
для кожного дня в schedules:
    якщо послуга serviceNumber відсутня в day.data.consularInstitutionService → пропустити
    start, end = час початку/кінця дня за timeZone установи (keepLocalTime)
    блокування = notWorkingDays цього consulIpnHash, що припадають на цей день
    для t від start з кроком slotInterval:
        якщо t + slotInterval > end → стоп (слот має вміститися повністю)
        якщо день сьогоднішній і t уже минув → пропустити
        якщо слот [t, t + slotInterval) не перетинається з жодним блокуванням → ВІЛЬНИЙ СЛОТ
повернути { result: true/false }
```

Деталі:

- **Сітка фіксована**: слоти починаються від часу відкриття (09:00, 09:10, 09:20…), а не від кінця
  попереднього запису.
- **Перетин**: слот `[t, t+i)` зайнятий, якщо `t + i > from` і `t < to` для будь-якого блокування.
- **Часовий пояс**: години прийому трактуються як «настінний» час за `timeZone` установи
  (`moment(...).utcOffset(tz, true)`). Блокування порівнюються як абсолютні моменти; оскільки
  в даних вони записані з тим самим зсувом, це рівнозначно порівнянню годин і хвилин з рядка.
- Слоти різних консулів незалежні: слот вільний, якщо він вільний хоча б в одного консула.

## 8. Чому стара версія програми показувала неіснуючі слоти

| Аспект | Стара програма | Сайт |
|---|---|---|
| Тривалість слоту | 5 хв | `serviceTime` послуги (для паспорта в Чикаго — 10 хв) |
| Сітка | будь-який вільний проміжок між блоками | фіксовані слоти від часу відкриття, слот має вміститися повністю |
| Записи розкладу | лише перший запис консула | усі записи, кожен у своєму періоді (`admissionSchedulePeriodDate`) |
| Неробочий час | 192 проміжки першого запису | 300 проміжків з усіх записів |
| Послуга | не враховувалась | дні без послуги не беруться |
| Дні | лише дати, що є в даних, і лише якщо в робочих годинах є хоч одне блокування | усі робочі дні від завтра до горизонту, без свят |
| Дата слоту | `new Date()` у часовому поясі браузера | дата консульства |

Головне джерело хибних результатів — 5-хвилинна сітка. Між записами о 08:50, 09:00 і 09:10
лишались 5-хвилинні «вікна», які програма показувала як доступні. Через це вона показувала
125 «bookable windows» там, де на сайті 0.

## 9. Як працює програма зараз

Застосунок — модуль `web/` (Vite + React + TypeScript), який віддає сервер `server/` (Fastify +
Postgres у Docker) на `http://localhost:3000`. Старий `slots.html` видалено 2026-10-21
([план переписування](plans/web-rewrite-plan.md), S8.T5).

| Шлях | Призначення |
|---|---|
| `web/` | Застосунок: сторінки «Слоти», «Моніторинг», «Налаштування»; домен (алгоритм розділів 6–7), монітор, адаптери — [web/README.md](../web/README.md) |
| `server/` | Віддає застосунок і API `/api/*`; журнали в Postgres назавжди — [server/README.md](../server/README.md) |
| `server/data/locations.json` | Довідник країн, установ, послуг і свят (розділ 10) |
| `extension/` | Розширення Chrome «e-Consul Helper»: токен сесії в застосунок, сповіщення про вхід, вибір слота в чернетці, власний журнал (див. [extension/docs/how-it-works.md](../extension/docs/how-it-works.md)) |

Запуск: `pnpm --dir server run db:up` (Postgres у Docker), `pnpm --dir web run build`,
`pnpm --dir server start` і відкрити `http://localhost:3000`. Без бази застосунок і моніторинг
працюють, а журнали чекають у пам'яті й доходять, коли база повернеться (`/api/health` → `db: down`).

Запити до e-Consul робить лише браузер, із токеном користувача; сервер їх не робить і токена не
бачить — у журнал іде лише опис запиту (метод, статус, тривалість, результат).

### Сторінки

| Сторінка | Що на ній |
|---|---|
| Бокове меню | Блок стану: моніторинг працює чи зупинено, відлік до наступної перевірки, сесія до … зі смужкою, розширення ✓/✗, «Запустити» / «Зупинити», «Перевірити». Бейдж «N нові» біля «Моніторинг» |
| «Слоти» | Відкривається на місяці **останнього відкритого дня** (горизонту), де з'являються нові дні, а не на поточному. Дані — з моніторингу, а до його першої перевірки (чи коли він не запущений) — останній календар із бази з приміткою «Показано останній збережений стан: перевірка о …»; розклад без зайнятих слотів нічого не малює (усе здавалося б вільним). «Наступне відкриття» (момент, час консульства, який день відкривається, часті перевірки), «Найближчі вільні» в діапазоні дат, календар місяця (кількість вільних, смужка зайнятих і неробочих, дні поза діапазоном приглушені, дні за горизонтом — «ще не відкрито»), панель дня (плитки вільних / зайнятих / неробочих слотів, нещодавні резервування, «Відкрити чернетку») |
| «Моніторинг» | Зведення за день (перевірки, нові вільні, резервування, скасування), журнал перевірок (рядок на перевірку: час, стан, результат, позначки, тривалість; дні розділені; запит у дорозі видно одразу зі статусом «в обробці»; сторінки по 15/25/50 рядків) з фільтрами «Усі», «Нові слоти», «Помилки», «Часті» і лічильниками разом із подіями розширення, журнал резервувань і зміни розкладу (той самий компактний вигляд, дні розділені, сторінки по 15/25/50; зміни розкладу — із завантаженням JSONL). Дані — з сервера |
| «Налаштування» | Що шукаємо (країна → установа → послуга, рядок параметрів, діапазон дат), сесія (стан токена, ручне введення), перевірки (інтервал, часті перевірки), бронювання (посилання на чернетку, автобронювання), сповіщення (дозволи, мітка заголовка вкладки, тестові сигнали) |
| Банери | «Увійдіть на e-consul…» (з розширенням, коли сесії немає), «Сесія скінчиться о …» (менше 30 хв), «Нові вільні слоти: …» з «Відкрити чернетку» |

Без вибраної установи «Слоти» й «Моніторинг» показують порожній стан із посиланням на
«Налаштування». Вибір, інтервал, діапазон дат, чернетка й мітка заголовка зберігаються в
`localStorage` під ключами (`slots.selection`, `slots.interval`,
`slots.dateRange`, `slots.draft`, `slots.schedule.<код>`, `slots.tabTitleMarks`).

### Моніторинг

1. Розклад (`public-calendar-get-actual-consuls-schedule`) запитується на першій перевірці і далі
   **раз на 30 хвилин** (і знову на наступній перевірці, якщо прийшов порожнім). Решта перевірок —
   **один запит** зайнятих слотів (`public-get-consuls-reserved-slots` для всіх консулів, що
   надають послугу), щоб не перевантажувати сесію.
2. Вільні слоти рахуються за розділами 6–7 (`web/src/domain/slots`).
3. Сповіщення — лише про **нові** слоти, яких не було в попередній перевірці. Слот, що зник і
   з'явився знову, — знову новий. Перша перевірка вважає новими всі знайдені.
4. Діапазон дат (необов'язковий, включно) фільтрує сповіщення, «нові» в журналі й слоти для
   розширення; календар показує всі. Новими вважаються лише слоти в діапазоні; слот поза діапазоном
   не стане новим, якщо діапазон потім розширити.
5. Зміна країни, установи чи послуги скидає стан: наступна перевірка бере розклад заново.
6. Вид перевірки: `Перевірка #12` — за розкладом, `(часта)` — у вікні частих перевірок, `(ручна)` —
   кнопка «Перевірити» (працює й без запущеного моніторингу; запущений планує наступну від неї).
7. Інтервал — випадковий між межами (типово 60–180 с, мінімум 10 с).
8. Кожна перевірка й кожен запит до e-Consul пишуться в журнал на сервері; зайняті слоти двох
   поспіль перевірок порівнюються — «зарезервовано» / «звільнено» йде в журнал резервувань.

#### Відкриття нових днів

За правилом горизонту (розділ 6, п. 3) день з'являється в календарі, коли час його відкриття
за `timeZone` установи стає раніше, ніж `зараз + numberWeeks тижнів − 1 день`. Отже, кожен новий
день відкривається рівно за `numberWeeks × 7 − 1` днів до свого часу відкриття — **щодня в годину
відкриття консульства** за `timeZone` установи. Для Чикаго (`GMT-06:00`, 09:00, 25 тижнів) це
**10:00 CDT** (після переходу на зимовий час — 09:00 CST), а відкривається день через 174 дні.
У цей момент з'являється цілий день вільних слотів.

Наслідки, які видно в розрахунку:

- нові дні відкриваються й у суботу: о 10:00 CDT у суботу 10.10.2026 відкривається п'ятниця
  02.04.2027; у неділю й понеділок нових днів немає (відкривалися б субота й неділя);
- якщо в дня кілька проміжків прийому (Нью-Йорк 09:00–12:00 і 14:00–17:00), кожен відкривається
  окремо, у свою годину;
- свята пропускаються.

Застосунок рахує ці моменти з розкладу (`web/src/domain/monitoring/releases.ts`): будує дні
календаря так, ніби зараз на 8 днів пізніше, і для кожного дня бере момент
`відкриття − (numberWeeks × 7 − 1) днів`. «Наступне відкриття» на сторінці «Слоти» показує
найближчий момент і вікно частих перевірок.

Планування з прапорцем:

| Коли | Наступна перевірка |
|---|---|
| Поза вікном, звичайна затримка не заходить у наступне вікно | Звичайний інтервал (наприклад, 60–180 с) |
| Звичайна затримка зайшла б за початок вікна | Рівно на початку вікна (за 2 хв до відкриття) |
| Усередині вікна (−2 хв … +3 хв) | Через 15–20 с, випадково |
| Перевірка почалася б за 15 с до відкриття … 15 с після нього (`QUIET_AT_RELEASE`) | Через 15 с після відкриття, з прапорцем чи без |

Тиша навколо моменту (з 2026-10-20, рішення власника): у цю мить розширення відкриває календар на сайті з тим самим
токеном («Далі» в момент відкриття, `extension/docs/how-it-works.md`). Першого разу перевірка застосунку, що почалась
о −0,25 с і тривала 5,3 с, летіла разом із запитами календаря, а календар одразу відповів «немає вільного часу». Менше
запитів з одного акаунта в цю мить — ще й менше схоже на бота.

Для Чикаго за налаштувань 60–180 с це приблизно 15–20 додаткових запитів на день.

Обмеження: розрахунок спирається на правило горизонту, встановлене емпірично (розділ 6). Моменти
перевірено розрахунком на розкладі Чикаго: 10:00 CDT збігається з розділом 6. Безпосередньо на
сайті в момент відкриття їх не звіряли. Чи справді в цю хвилину з'являються вільні слоти,
покаже журнал моніторингу перших днів.

Сповіщення:

| Подія | Звук | Нотифікація | Що відбувається |
|---|---|---|---|
| Нові вільні слоти | Дзвіночок: три висхідні ноти (880–1109–1319 Гц, синусоїда), тричі | «Нові вільні слоти: <установа>» з датами й часом. Клік відкриває чернетку або нову заявку на сайті | Моніторинг триває; банер нових слотів; заголовок вкладки 🟢 (якщо мітку не вимкнено) |
| Токен не працює (HTTP 401/403) | «Розбите скло»: спалах білого шуму (high-pass 1,8 кГц) з різким спадом і 10–14 коротких «дзенькотів» 3–6 кГц з випадковими затримками, двічі (~2,5 с) | «Сесія e-consul завершилась» (з розширенням — його системна нотифікація з кнопкою «Увійти») | Моніторинг **зупиняється**; заголовок вкладки 🔴. Без розширення: увійдіть на e-consul, введіть новий токен у «Налаштуваннях» і запустіть знову. З розширенням новий токен приходить сам, і моніторинг **запускається знову** із записом «Відновлено після входу» |
| Інша помилка (500, мережа) | — | — | Запис у журнал, моніторинг триває |

Моніторинг, зупинений кнопкою «Зупинити», після нового токена не відновлюється.

Нотифікації створюються з `requireInteraction: true`, тобто не закриваються самі. Дозвіл на
нотифікації браузер запитує під час першого запуску; без нього звук однаково грає. Звук на вкладці
вмикається першим кліком на сторінці (вимога браузера).

Записи не змінюються й не видаляються. Зміни розкладу: кожне оновлення розкладу порівнюється з

`baseline`, далі — лише справжні зміни (додано чи прибрано запис розкладу консула, змінились години
чи набір послуг, додались або прибрані неробочі проміжки; ті, що просто минули, змінами не
вважаються). Завантаження у JSONL — у форматі старого `logs/schedule-changes.jsonl`:


## 10. Файл locations.json

Знятий 2026-10-08 з довідників розділу 4 і функції `holidays`. Структура:

```json
{
  "about": "…",
  "generatedAt": "2026-10-08",
  "holidays": {
    "all": ["2026-12-25"],
    "byService": { "1": ["2026-11-21..2026-11-27"], "60": ["…"], "62": ["…"] }
  },
  "services": { "1": "Оформлення закордонного паспорта", "…": "…" },
  "institutions": [
    {
      "code": "1000000510",
      "name": "Генеральне консульство України у Г'юстоні",
      "countryCode": "840",
      "country": "США",
      "timeZone": "GMT-05:00",
      "numberWeeks": 25,
      "serviceMinutes": { "1": 10, "4": 15, "…": "…" }
```

- `code` — `unitId` установи, тобто `institutionCode` для API.
- `serviceMinutes` — послуги установи і `serviceTime` кожної, тобто тривалість слоту.
- Свята записані датами `YYYY-MM-DD` або діапазонами `YYYY-MM-DD..YYYY-MM-DD` (включно).

### Як оновити locations.json

Довідники відкриваються лише з токеном, тому оновлювати файл найпростіше з консолі браузера
на сторінці e-consul.gov.ua під своєю сесією. Скрипт нижче збирає файл і пропонує його зберегти.
Свята він бере з поточного файлу: їх треба звірити вручну (розділ 5).

```js
const tok = localStorage.getItem('token');
const call = method => fetch('https://my.e-consul.gov.ua/external_reader', {
  method: 'POST', headers: { 'content-type': 'application/json', token: tok },
  body: JSON.stringify({ service: 'e-queue-register', method, filters: {} })
```

## 12. Обмеження та що оновлювати вручну

- **Свята** беруться з `locations.json`. Сайт рахує їх із даних заявки, і ці дати зміняться
  (наприклад, на 2027 рік). Перевіряти їх варто разом з оновленням файлу.
- **Довідник** (`locations.json`) — знімок на 2026-10-08. Тривалість послуг, горизонт і склад
  установ можуть змінитися; як оновити — у розділі 10.
- **Горизонт** (розділ 6, п. 3) встановлений емпірично і підтверджений на Чикаго й Г'юстоні.
- **Перевірка на кроці 3.** Сайт може заблокувати запис ще до календаря («Запис … наразі
  недоступний»). Програма цього не бачить і рахує слоти лише за розкладом і зайнятими записами.
- **Сьогоднішній день** не перевіряється, бо запис можливий лише з завтрашнього (`startDayMove = 1`).
- **Моніторинг працює, лише поки відкрита вкладка** і комп'ютер не спить. У фоновій вкладці Chrome
  може затримувати таймери до хвилини, тож фактичний інтервал іноді трохи довший.
- **Звук** можна відтворити лише після кліку на сторінці, тому він «вмикається» кнопкою Start
  (або тестовою кнопкою). Після перезавантаження сторінки моніторинг, що працював, **відновлюється
сам**, щойно розширення передасть токен (прапорець `slots.monitoring` у `sessionStorage`: нова
вкладка його не успадковує, «Зупинити» його знімає, завершена сесія — ні). Без розширення
моніторинг треба запустити знову; звук після перезавантаження вмикається першим кліком.
- **Нотифікації на macOS** мають бути дозволені для Chrome у «Системних параметрах → Сповіщення».
  Щоб нотифікація не зникала сама, стиль сповіщень Chrome там має бути «Сповіщення» (Alerts),
  а не «Банери».
- **Ознака завершеної сесії** — HTTP 401/403 від API (так сервер відповідає на запит без
  токена). Якщо сервер повідомить про це інакше, моніторинг запише помилку в журнал і продовжить.
- **Токен.** Запити йдуть напряму з браузера із JWT. Токен має термін дії. Часті запити можуть
  обірвати сесію на сайті, тож краще не натискати Fetch надто часто.
- **Зміни на сайті.** Шаблон форми та алгоритм worker'а можуть змінитися. Хеші файлів
  (`worker.51fddf6db8eb24d71441.worker.js`, `main.99eaf1156387a8a1ac2d.js`) актуальні на 2026-10-08.

## 13. Як дослідити сайт повторно

1. Відкрити заявку на кроці 3 («Консульська послуга») з активною сесією.
2. У консолі перехопити повідомлення до worker'а **до** переходу на крок 4:

   ```js
   window.__wmsgs = [];
   const opm = Worker.prototype.postMessage;
   Worker.prototype.postMessage = function (m) {
     if (m && m.slotIntervalEval !== undefined) window.__wmsgs.push(m);
     return opm.apply(this, arguments);
   };
   ```

3. Натиснути «Далі». У `window.__wmsgs[0]` будуть `schedules`, `notWorkingDays`, `slotIntervalEval`
   та інші вхідні дані розрахунку. Переходи кнопками «Далі»/«Назад» не перезавантажують сторінку,
   тож перехоплювач працює і для наступних установ.
4. Схема календаря:
   `GET https://my.e-consul.gov.ua/document-templates/161374001` із заголовком
   `token: localStorage.token` → `data.jsonSchema.properties.dateAndTimeVisitInfo.properties.calendar`.
5. Код розрахунку — обробник `self.addEventListener("message", …)` у файлі
   `worker.<hash>.worker.js`. Його URL видно у вкладці Network під час кроку 4.
6. Довідники для кроків 2–3 — розділ 4.

## 14. Бронювання: як сайт займає слот і що бачить сервер

Дослідження 2026-10-08. Висновки зроблені з коду фронтенду (`main.99eaf1156387a8a1ac2d.js`,
lazy-чанк `9412.<hash>.js` зі сторінкою задачі), шаблону форми `document-templates/161374001`
і перевірки HTTP-заголовків. **Сам запит бронювання не виконувався і не перехоплювався**, бо він
створив би справжній запис. Тому тіла запитів нижче відновлені з коду, а не з мережевого журналу.

### 14.1. Ланцюжок запитів

Окремого запиту «забронювати слот» немає. Бронювання — частина задачі «Запис на візит»:

| # | Запит | Що робить |
|---|---|---|
| 1 | `POST /tasks` | Створює задачу (`workflowTemplateId` 161374, `taskTemplateId` 161374001) і порожній документ. Чернетка видаляється через добу (`deleteDraftAfterCreateAt: "1d"`) |
| 2 | `PUT /documents/{documentId}` | Зберігає дані форми. Викликається на кожному кроці, зокрема з `dateAndTimeVisitInfo.calendar.chosenSlots` на кроці 4 |
| 3 | `POST /documents/{documentId}/external-reader/check` | Перевірки на кроках 3–4, зокрема **бронювання** (14.2) |
| 4 | `POST /documents/{documentId}/validate?commit=true` | Перевірка документа перед відправкою |
| 5 | `POST /tasks/{taskId}/commit` | Відправка заявки. Тіло `{}` |

Усі запити йдуть на `https://my.e-consul.gov.ua` із заголовками `content-type: application/json`
і `token: <JWT>`, з `cache: "reload"`. Інших заголовків API-клієнт сайту не додає (заголовок
`debug-user-id` лише в режимі налагодження).

Підпис не потрібен: у шаблоні `signRequired`, `isP7sSign`, `diiaSign` і `pdfRequired` дорівнюють
`false`. Після відправки сайт показує «Дякуємо, ми обробляємо ваш запит», а результат приходить на
email за кілька хвилин.

### 14.2. Перевірки `externalReaderCheck` на кроці 4

Перевірки описані в шаблоні як контроли `externalReaderCheck` безпосередньо в об'єкті кроку
(не в `properties`). Фронтенд надсилає на `external-reader/check` лише:

```json
{
  "service": "e-queue-register",
  "method": "public-check-and-book-appointments",
  "path": "dateAndTimeVisitInfo.externalReaderCheck_CreatingVisitAppointment"
}
```

Якщо для методу ввімкнена капча, додається ще поле `captchaPayload` (14.4). **Фільтри запиту
обчислює сервер** з функцій у шаблоні та даних збереженого документа. Клієнт їх не передає.

| Контрол (крок 4) | Метод | Фільтри (з документа) |
|---|---|---|
| `externalReaderCheck_AppointmentVisit` | `public-get-booked-appointments` | `recipientNames`, `serviceNumber` — чи є вже запис |
| `externalReaderCheck_CreatingVisitAppointment` | **`public-check-and-book-appointments`** | див. нижче |
| `externalReaderCheck_waitingQueue` | `public-get-queue-appointments` | `serviceNumber` — чи заявник у черзі очікування |

Фільтри бронювання:

| Фільтр | Звідки |
|---|---|
| `applicant` | `{ applicantEmail, applicantPhone, applicantBirthDate, applicantGender }` з `calculated` |
| `institutionCode` | `placeOfVisitInfo.consularInstitution.data.unitId` |
| `serviceNumber` | `consularServiceInfo.service.data.serviceNumber` |
| `applicantForeignDoc` | `calculated.foreignOrStatelessFile` |
| `slots` | `chosenSlots` → `[{ receptionDateAndTimeFrom, receptionDateAndTimeTo, consuls: [{ consulIpnHash }] }]` |
| `status` | `2`, якщо в заявника вже є запис (`isHasReservedSlot`), інакше `1` |

На кроці 3 є ще перевірки `public-get-booked-applicant-appointments`,
`public-get-actual-consuls-schedule` (з `serviceNumber`), `oberig / get-evod-status` (для чоловіків
призовного віку) і `dracs` (для запису дитини).

### 14.3. Новий запис і перенесення

- `status: 1` — **новий запис**. Слот займається одразу запитом `public-check-and-book-appointments`.
- `status: 2` — **перенесення** наявного запису. Новий слот тримається **1 годину**
  (`onResponse.startAutoCommitTimer`, `timer: '1h'`). На сторінці з'являється таймер
  «Підтвердіть зміну дати та часу запису», а кнопка завершення — «Підтверджую». Якщо не
  підтвердити, показується «Час бронювання сплив».
- Якщо вільного часу немає, кнопка завершення — «Записатись в чергу очікування». Схоже, такий самий
  текст кнопка має й поки йде пошук і слот не вибрано: тож «немає часу» визначається лише за
  повідомленням «На жаль, зараз немає вільного часу», а не за кнопкою (відкриття 2026-10-22, див.
  `extension/INSIGHTS.md`).

### 14.4. Що може відстежити сервер

| Механізм | Стан на 2026-10-08 | Що це означає для програми |
|---|---|---|
| **Cloudflare** перед `e-consul.gov.ua` і `my.e-consul.gov.ua` | `curl` отримує 403 і на статичні JS-файли сайту, і на `POST /external_reader`, зокрема на CORS preflight. `GET /test/ping` проходить. Ставиться кукі `__cf_bm` | Запити до API можливі лише з реального браузера. Сервер на Go напряму бронювати не зможе |

### 14.5. Чи можуть скасувати запис

Технічно сервер може відрізнити бронювання з програми від бронювання із сайту: за `Origin`,
журналами Cloudflare і таймінгами (наприклад, бронювання за секунду після появи слота без
переглядів календаря). Чи робиться така перевірка і чи скасовуються такі записи, ззовні встановити
неможливо: у коді фронтенду ознак цього немає, рішення ухвалює сервер. Найімовірніша перша реакція
адміністраторів — увімкнути капчу на `public-check-and-book-appointments`.

**Оновлено 2026-10-24 (рішення власника).** Після відкриттів 2026-10-23/24, де сайт відхиляв кожне
«Підтвердити» («Сервіс недоступний») перші ~3.5 хв, власник вирішив **перевірити** пряме бронювання по API:
теорія — у перші секунди навантаження менше, тож `public-check-and-book-appointments` може спрацювати. За
галочкою «Бронювати напряму через API» (`directApiBook`, типово вимкнена). Фаза 1 (v0.14.9) — лише **розвідка**:
розширення читає `GET /tasks/{id}` і `GET /documents/{id}` та логує справжню форму `chosenSlots` (подія
`api-recon`), бо тіла §14.1–14.2 відновлені з коду й ніколи не перевірялися. Нічого не бронює. Фаза 2 (після
звірки форм) — реальний `PUT /documents` + `check`. Ризики §14.5 (виявлення за `Origin`/таймінгами, можлива
капча) власник прийняв для тесту.

Тому програма **не бронює сама**. Вона знаходить слоти й сповіщає, а бронювання робиться на сайті
(14.6), бажано з заздалегідь підготовленої чернетки. Тоді всі запити, заголовки, кукі Cloudflare й історія задачі такі самі, як у звичайного
користувача, а якщо капчу ввімкнуть, сайт її покаже.

### 14.6. Кнопка «Book on e-consul» і чернетка

Сайт має маршрути `/tasks/create/:workflowTemplateId/:taskTemplateId` і
`/tasks/create/:workflowTemplateId` (так само зроблені посилання в меню сайту, наприклад
`/tasks/create/161388/161388001`). Для запису на візит це

```
https://e-consul.gov.ua/tasks/create/161374/161374001
```

- Посилання створює нову задачу й відкриває крок 1.
- Пропустити кроки не можна. Сторінка створення не читає параметрів для попереднього заповнення
  (з URL читаються лише `lang`, `code`, `state`, `redirect_uri` для входу і службові параметри),
  а бронювання сервер будує з даних збереженого документа (14.2).
- Без активної сесії сайт веде на `id.e-consul.gov.ua`. Адреса `/tasks/create/…` зберігається
  в `localStorage.redirectURL`, тож після входу сайт повертає на нову заявку.
- Кожне відкриття створює нову чернетку. Невідправлені чернетки сайт видаляє через добу.

#### Чернетка

Щоб у момент появи слота не проходити кроки 1–3, чернетку готують заздалегідь **на сайті**:

1. Відкрити нову заявку (кнопка **↗ Book on e-consul** з порожнім **Draft link**) і пройти кроки
   1–3: заявник, установа, послуга. Сайт сам обчислить поля `calculated` і виконає перевірки кроку 3.
2. На кроці 4 нічого не вибирати. Скопіювати адресу сторінки: `https://e-consul.gov.ua/tasks/{taskId}/…`.
3. Вставити її в поле **Draft link**.
4. Коли програма знаходить слот, кнопка або клік по нотифікації відкривають чернетку. Перейти на
   крок 4, вибрати слот, натиснути «Далі». Календар кроку 4 завантажується заново, тож слоти актуальні.

Програма приймає лише адреси виду `https://e-consul.gov.ua/tasks/<id>` або
`https://e-consul.gov.ua/tasks/<id>/<крок>`. Будь-яка інша адреса (зокрема `/tasks/create/…`
і `/tasks/my-tasks`) вважається помилкою, і відкривається нова заявка.

Обмеження:

- **Чернетка живе добу** від створення (`deleteDraftAfterCreateAt: "1d"`). Програма знає лише, коли
  посилання вставили, і через 24 години від цього моменту показує попередження. Чернетку треба
  створювати заново щодня.
- **Не перевірено**, чи повторює сайт перевірки кроку 3 (`oberig`, наявні записи, черга), коли
  відкривається збережена чернетка. Якщо повторює, перехід на крок 4 займе кілька секунд.
- Якщо сесія на сайті скінчилась, сайт попросить увійти й після входу поверне на чернетку.

#### Де в програмі

- поле **Draft link** і кнопка **↗ Book on e-consul** у блоці Monitoring;
- така сама кнопка в заголовку блоку **Available Booking Windows**;
- клік по нотифікації «New free slots».

Розширення (з v0.5.0) створює чернетку саме: після входу на e-consul, якщо чернетки немає чи вона
прострочена, і за кнопкою «Створити чернетку» (кроки 1–3 з установою й послугою з налаштувань
застосунку, ~20 с; опис — [extension/docs/how-it-works.md](../extension/docs/how-it-works.md)).
Поки моніторинг працює без чернетки, застосунок показує червоний банер «Немає чернетки».

План розширення Chrome, яке створюватиме чернетку й вибиратиме слот, —
[extension/plans/extension-plan.md](../extension/plans/extension-plan.md).

Константи `BOOKING_URL`, `DRAFT_URL_RE` — у `web/src/domain/booking/booking-url.ts`. Якщо сайт змінить номер
процесу, його видно в адресі сторінки після «Запис на візит» → «Створити».

### 14.7. Чи заповнювати чернетку прямими запитами до API

Ідея: заздалегідь `POST /tasks` і `PUT /documents/{id}` з даними кроків 1–3, а коли з'явиться слот —
дописати `chosenSlots` і викликати `public-check-and-book-appointments`. Технічно запити ті самі,
але робити так **не варто**:

| Проблема | Чому |
|---|---|
| Поля `calculated` | Фільтри бронювання (email, телефон, дата народження, стать, `recipientsNameArrays`, `statusArray`) сервер бере з `calculated`, а ці поля обчислює **фронтенд** функціями `calcTriggers` шаблону (зокрема sha256 від ІПН). Неточне відтворення дасть запис із хибними даними або помилку, і перевірити це можна лише справжнім бронюванням |
| Перевірки кроку 3 | `oberig / get-evod-status`, наявні записи, черга очікування. Без них документ неповний: його або відхилить `validate?commit=true`, або запис створиться в обхід перевірки, яку сайт робить усім, — і це законна підстава його скасувати |
| Сліди | `activityLog` без звичайних кроків і переглядів, усі запити з `Origin: http://localhost:3000`. Через Cloudflare запити все одно мусять іти з браузера |
| Крихкість | Будь-яка зміна шаблону (десятки `calcTriggers`) непомітно зламає бронювання саме в момент, коли з'явився слот |

Чернетка, підготовлена на сайті (14.6), дає ту саму економію часу без цих ризиків.
